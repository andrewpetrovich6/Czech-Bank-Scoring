## 0. Бизнес-постановка

**Ситуация.** Банк выдаёт кредиты клиентам, у которых уже есть счёт в этом банке. Часть кредитов не возвращается, и банк теряет деньги.

**Вопрос.** Можно ли по истории операций по счёту и данным о клиенте **заранее**, в момент выдачи, предсказать, что кредит станет проблемным?

**Что даст ответ бизнесу:**
- правило одобрения: кому выдавать кредит, а кому нет;
- понимание компромисса «одобряем больше заявок ↔ получаем больше плохих кредитов»;
- список признаков риска, понятных кредитному аналитику (например, «уход баланса в минус»).

**Почему логистическая регрессия:**
- даёт **вероятность** дефолта, а не просто «да / нет»;
- **интерпретируема**: у каждого признака есть коэффициент, и его можно объяснить регулятору и бизнесу. Поэтому в банковском скоринге это стандарт;
- устойчива на **маленьких данных** (у нас 682 кредита), где сложные модели переобучаются.

## 1. Данные

**Источник:** [The Berka Dataset — Kaggle](https://www.kaggle.com/datasets/marceloventura/the-berka-dataset). Это реальные обезличенные данные чешского банка из соревнования PKDD'99, период 1993–1998.

| Таблица | Строк | Содержимое | Ключи |
|---|---:|---|---|
| `account` | 4 500 | счета: район, частота выписок, дата открытия | `account_id` (PK), `district_id` (FK) |
| `client` | 5 369 | клиенты: зашифрованные дата рождения и пол, район | `client_id` (PK), `district_id` (FK) |
| `disp` | 5 369 | связь клиент ↔ счёт и роль (OWNER / DISPONENT) | `disp_id` (PK), `client_id`, `account_id` (FK) |
| `trans` | ~1 056 000 | операции: дата, тип, сумма, остаток после операции | `trans_id` (PK), `account_id` (FK) |
| `loan` | 682 | кредиты: дата, сумма, срок, платёж, **статус** | `loan_id` (PK), `account_id` (FK) |
| `card` | 892 | карты: тип (junior / classic / gold), дата выдачи | `card_id` (PK), `disp_id` (FK) |
| `order` | 6 471 | постоянные платёжные поручения (автоплатежи) | `order_id` (PK), `account_id` (FK) |
| `district` | 77 | районы: население, безработица, средняя зарплата, преступность | `district_id` (PK) |

**Статусы кредита:**

| Код | Значение | Класс |
|---|---|---|
| A | кредит закрыт, всё выплачено | хороший (0) |
| B | кредит закрыт, не выплачен | **плохой (1)** |
| C | кредит действует, платежи в порядке | хороший (0) |
| D | кредит действует, есть долг | **плохой (1)** |

Плохих кредитов **76 из 682 (≈ 11%)**. Это несбалансированная задача.

**Известные ограничения (честно пишем их в README):**
- выборка маленькая, поэтому оценки качества «шумные», и нужна кросс-валидация;
- данные старые (1990-е) и одной страны, поэтому выводы иллюстративны, а не универсальны;
- статус C — «кредит ещё идёт»; часть таких кредитов в будущем может стать плохой.

## Этап 4. Витрина признаков (SQL) — главная SQL-часть

**Файл:** `sql/05_features.sql`
**Результат:** таблица `features`, **одна строка = один кредит**, все признаки + `is_bad`. Сохраняем её в `data/processed/features.csv`.

### ⚠️ Главное правило: защита от утечки данных (data leakage)

Признаки считаются **только по операциям, совершённым ДО даты выдачи кредита**:

```sql
WHERE t.date < l.date
```

**Почему это критично.** Если взять операции после выдачи, модель «подсмотрит будущее»: например, увидит, что клиент перестал вносить деньги. На исторических данных качество будет отличным, а в реальности модель бесполезна: в момент выдачи этих операций ещё нет. Это обязательно описываем в README.

### Признаки

**Поведение по счёту** (окна: 90 и 180 дней до выдачи + вся история):

| Признак | Как считается | Гипотеза |
|---|---|---|
| `balance_mean_90d` | средний остаток за 90 дней до кредита | больше денег → меньше риск |
| `balance_min_90d` | минимальный остаток | низкий минимум → финансовые трудности |
| `balance_std_90d` | разброс остатка | нестабильность → риск |
| `n_negative_balance` | сколько раз остаток уходил в минус | ключевой сигнал риска |
| `n_sanction_interest` | число штрафных начислений (`SANKC. UROK`) | прямой признак проблем |
| `n_trans_90d` | число операций | активность клиента |

**Доходы и нагрузка:**

| Признак | Как считается | Гипотеза |
|---|---|---|
| `income_month_mean` | средний ежемесячный приход | выше доход → ниже риск |
| `income_month_cv` | коэффициент вариации приходов (std / mean) | нерегулярный доход → риск |

**Кредит и клиент:**

| Признак | Как считается |

| `card_type` | тип карты (none / junior / classic / gold) — **только карты, выданные до кредита** |

## Этап 6. Модель: логистическая регрессия

**Файл:** `notebooks/02_model.ipynb`

### 6.1. Разбираемся с сигмоидой
- [ ] Нарисовать сигмоиду σ(z) = 1 / (1 + e<sup>−z</sup>) для z от −8 до 8
- [ ] Понять: модель считает линейную комбинацию z = b₀ + b₁x₁ + … + bₙxₙ, а сигмоида превращает её в **вероятность от 0 до 1**
- [ ] Понять: обучение подбирает коэффициенты b так, чтобы минимизировать **log-loss**, то есть максимизировать правдоподобие

### 6.2. Подготовка
- [ ] Отобрать признаки по итогам EDA; убрать сильно коррелирующие дубли
- [ ] Закодировать категориальные признаки (`OneHotEncoder` для `card_type`, `gender`)
- [ ] Разбить на train / test **стратифицированно** (`stratify=y`, 75 / 25) — чтобы доля плохих (11%) была одинаковой в обеих частях
- [ ] Масштабировать числовые признаки (`StandardScaler`): логистическая регрессия с регуляризацией чувствительна к масштабу

### 6.3. Обучение
- [ ] Собрать `Pipeline` (`ColumnTransformer` + `LogisticRegression`), чтобы масштабирование обучалось **только на train**: это ещё одна защита от утечки
- [ ] Учесть дисбаланс классов: `class_weight='balanced'`
- [ ] Подобрать силу регуляризации `C` через `GridSearchCV` + `StratifiedKFold(5)` по метрике ROC-AUC
- [ ] Сравнить с простыми базовыми моделями (baseline):
  - «всех одобрить» (константа)
  - логистическая регрессия на 1–2 признаках (например, только `balance_min_90d`)

**Зачем baseline:** без него непонятно, хороша модель или нет. «AUC 0,80» ничего не значит, пока не видно, что простое правило даёт, например, 0,65.
